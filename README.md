# Week 4 - File Uploads, Pagination, Filtering & Search

## Project Description
This project adds file-upload support to tasks and upgrades the task list endpoint with pagination, filtering, and search, on top of an existing authenticated (JWT) task management API.

## Tech Stack
- **Backend:** Node.js, Express.js
- **Database:** MongoDB (Atlas)
- **Authentication:** JWT (jsonwebtoken), bcryptjs
- **File Uploads:** Multer + Cloudinary (cloud storage)
- **Frontend:** HTML, CSS, JavaScript (Vanilla)

## Setup Instructions

### Backend Setup
1. Navigate to the server folder: `cd server`
2. Install dependencies: `npm install`
3. Create a .env file (copy .env.example and fill in real values):
   - MONGODB_URI=your_mongodb_connection_string
   - JWT_SECRET=your_secret_key
   - PORT=5000
   - CLOUDINARY_CLOUD_NAME=your_cloud_name
   - CLOUDINARY_API_KEY=your_api_key
   - CLOUDINARY_API_SECRET=your_api_secret
4. Start the server: `node server.js`

### Frontend Setup
1. Navigate to the client folder
2. Open register.html in a browser to create an account
3. Log in via login.html
4. You will be redirected to dashboard.html to manage tasks

## Feature: File Uploads (Cloudinary)

### How It Works
1. The frontend sends task data (title, description, attachment) as multipart/form-data using the browser's FormData object, because a file cannot be sent as JSON text.
2. The multer middleware (uploadMiddleware.js) intercepts the request before the route handler runs.
3. The uploaded file is validated:
   - **Allowed types:** JPG, PNG, PDF only
   - **Max size:** 5MB
   - Invalid files are rejected with a clear error message and are never uploaded.
4. Instead of saving files to local disk, multer is configured with multer-storage-cloudinary, which uploads the accepted file directly to a Cloudinary cloud storage bucket, inside an asl-week4-uploads folder.
5. Cloudinary returns a permanent URL for the uploaded file, which is stored on the Task document as the attachment field.
6. For image attachments, a thumbnail URL is generated by editing the Cloudinary URL with resize transformation parameters (w_150,h_150,c_fill), avoiding any need to process the image ourselves. PDFs do not get a thumbnail.
7. Because files live on Cloudinary, no local uploads/ folder or static file-serving route is required for new uploads.

### Example Request (multipart/form-data)
POST /api/tasks
- title: "Grocery Shopping"
- description: "Buy milk and eggs"
- attachment: (file)

## Feature: Pagination, Filtering & Search

### Offset Pagination
GET /api/tasks

| Query Parameter | Purpose | Example |
|---|---|---|
| page | Which page of results to return (default: 1) | ?page=2 |
| limit | How many results per page (default: 5) | ?limit=10 |
| completed | Filter by completion status (true or false) | ?completed=true |
| search | Partial, case-insensitive match on task title | ?search=grocery |
| sortBy | Field to sort by (createdAt or title) | ?sortBy=title |
| order | Sort direction (asc or desc) | ?order=asc |

#### Combined Example
GET /api/tasks?page=1&limit=5&completed=false&search=shopping

This returns page 1, 5 results per page, only incomplete tasks, whose title contains "shopping" (case-insensitive).

#### Response Shape
```json
{
  "tasks": [ ... ],
  "currentPage": 1,
  "totalPages": 3,
  "totalTasks": 12
}
```

### Cursor-Based Pagination (Bonus)
GET /api/tasks/cursor

Offset pagination can skip or repeat records if tasks are added or deleted while a user is paging through results. Cursor pagination avoids this by using the last-seen task's _id as a marker for where the next page should start, instead of a page number.

| Query Parameter | Purpose | Example |
|---|---|---|
| limit | How many results per page (default: 5) | ?limit=5 |
| completed | Filter by completion status | ?completed=false |
| search | Partial, case-insensitive match on task title | ?search=grocery |
| cursor | The _id of the last task from the previous page | ?cursor=64f1... |

#### How to Use It
1. Call the endpoint without a cursor to get the first page.
2. The response includes a nextCursor value (the _id of the last task returned).
3. Call the endpoint again, passing that value as ?cursor=..., to get the next page.
4. When nextCursor is null, there are no more results.

#### Response Shape
```json
{
  "tasks": [ ... ],
  "nextCursor": "64f1a2b3c4d5e6f7g8h9i0j1"
}
```

Both pagination endpoints respect ownership - a user only ever sees their own tasks, regardless of the filters applied.

## Protected Endpoints

| Method | Endpoint            | Protected | Ownership Check | Notes |
|--------|----------------------|-----------|------------------|-------|
| POST   | /api/auth/register   | No        | -                | |
| POST   | /api/auth/login      | No        | -                | Rate limited (5/15min) |
| POST   | /api/tasks           | Yes       | -                | Accepts multipart/form-data with optional file (uploaded to Cloudinary) |
| GET    | /api/tasks           | Yes       | Returns only own tasks | Offset pagination - supports page, limit, completed, search, sortBy, order |
| GET    | /api/tasks/cursor     | Yes       | Returns only own tasks | Cursor pagination - supports limit, completed, search, cursor |
| GET    | /api/tasks/all       | Yes       | Admin only       | |
| PUT    | /api/tasks/:id       | Yes       | Yes              | |
| DELETE | /api/tasks/:id       | Yes       | Yes              | |

## Features Implemented
- File upload with type and size validation (Multer)
- Uploaded files stored on Cloudinary cloud storage and referenced on the task record
- Automatic thumbnail generation for image attachments via Cloudinary URL transformations
- Offset/limit pagination on the task list endpoint
- Cursor-based pagination on a dedicated endpoint (bonus)
- Filtering by completion status
- Case-insensitive partial search by title
- Sorting by date or title (bonus)
- Frontend upload form, search box, filter dropdown, and pagination controls
- Existing authentication/ownership rules preserved throughout
